# Update server

The fork ships two update surfaces. Both live on the same R2 bucket
and are generated by `tools/release/generate_update_manifests.py` as
part of the `.github/workflows/update-manifest.yml` workflow.

## Surface #1 — Chromium-internal updater (Omaha 4)

Chromium's `components/update_client` polls an XML endpoint at a
configurable URL. The fork's build patches that URL to point at our
R2 bucket:

```
GET https://cdn.bramburn.com/browseros/windows/update_check.xml
```

The endpoint serves an Omaha-4 `update_check` response. Example:

```xml
<?xml version='1.0' encoding='UTF-8'?>
<response protocol="3.0" server="prod">
  <daystart elapsed_days="262"/>
  <app appid="{B49B6F23-...}" status="ok">
    <updatecheck status="ok">
      <urls>
        <url codebase="https://cdn.bramburn.com/browseros/"/>
      </urls>
      <manifest version="0.1.0">
        <packages>
          <package hash="sha256=abc123..." name="BrowserOS_v0.1.0_win-x64.exe" size="157286400" required="true"/>
        </packages>
      </manifest>
    </updatecheck>
  </app>
</response>
```

The browser then:
1. Downloads the `.exe` in the background.
2. Shows the "Update available — restart to update" toast on a quiet
   moment.
3. On user action, restarts into the new version with tabs preserved.

The fork's app ID is a stable GUID — see `BROWSEROS_APP_ID` repo
variable in the [Release](release) page. Changing it forces every
user to re-enroll, so don't change it casually.

### End-to-end test

1. Build + publish v1 of the fork.
2. Update the in-browser updater URL via the build patch
   (`packages/browseros/chromium_patches/` — TBD location).
3. Build + publish v2 with `bump_version.py --mode offset+build`.
4. Install v1 on a clean VM. Confirm:
   - On next browser restart, the toast appears within a few minutes.
   - Clicking "restart" preserves all open tabs.
5. After restart, confirm v2 is running and update_client polls show
   no further update available.

## Surface #2 — External appcast (Sparkle RSS)

A Sparkle-style RSS feed served at:

```
GET https://cdn.bramburn.com/browseros/windows/appcast.xml
```

Example:

```xml
<?xml version="1.0" encoding="utf-8"?>
<rss xmlns:sparkle="http://www.andymatuschak.org/xml-namespaces/sparkle" version="2.0">
  <channel>
    <title>BrowserOS Windows</title>
    <link>https://github.com/bramburn/BrowserOS/releases</link>
    <description>...</description>
    <language>en</language>
    <item>
      <title>BrowserOS 0.1.0</title>
      <link>https://github.com/bramburn/BrowserOS/releases/tag/browseros-windows-v0.1.0</link>
      <sparkle:version>0.1.0</sparkle:version>
      <sparkle:shortVersionString>0.1.0</sparkle:shortVersionString>
      <sparkle:minSystemVersion>10.0.17763</sparkle:minSystemVersion>
      <pubDate>Sat, 19 Sep 2026 16:00:00 +0000</pubDate>
      <enclosure url="https://cdn.bramburn.com/browseros/0.1.0/BrowserOS_v0.1.0_win-x64.exe"
                 sparkle:os="windows-x64"
                 length="157286400"
                 type="application/octet-stream"/>
      <description>SHA-256: abc123...</description>
    </item>
  </channel>
</rss>
```

### Consumers

- `browseros-cli` (Go) — add a `check-update` subcommand that polls
  this URL and exits 0 if a newer version is available.
- External build dashboards / monitoring.
- The MCP server itself can advertise "new version available" via the
  existing `windows` tool (post-MCP work).

## Surface #3 — JSON pointer (lightweight)

For tools that don't want to parse XML:

```
GET https://cdn.bramburn.com/browseros/latest.json
```

```json
{
  "version": "0.1.0",
  "url": "https://cdn.bramburn.com/browseros/0.1.0/BrowserOS_v0.1.0_win-x64.exe",
  "sha256": "abc123...",
  "size": 157286400,
  "channel": "stable",
  "app_id": "{B49B6F23-...}",
  "published_at": "2026-09-19T16:00:00+00:00"
}
```

## Signing

The Omaha-4 response itself does **not** need to be signed — the
signature is over the **payload** (the `.exe` download). Chromium's
`update_client` verifies the SHA-256 in `<package hash="sha256=...">`
against the downloaded file before applying it.

For full delta-update signing (smaller payloads, like real Chrome),
we'd add RSA signatures over the differential update. That's a v2
feature — for v1, full `.exe` download + SHA-256 is sufficient.

## Generating the manifests

```bash
# Manual generation (used by CI and the manual fallback path)
python3 tools/release/generate_update_manifests.py \
  --version 0.1.0 \
  --sha256 abc123... \
  --size 157286400 \
  --app-id "{B49B6F23-...}" \
  --r2-prefix browseros \
  --cdn-base https://cdn.bramburn.com \
  --output-dir /tmp/out
```

Produces `update_check.xml`, `appcast.xml`, and `latest.json` in the
output directory. The CI workflow then uploads all three to R2.
